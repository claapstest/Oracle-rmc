- Frontend omission of `context` (GAP-2)
- Any auth-logic refactor
 
Findings are recorded, not fixed. Functional changes ship as separate approved changes, per the story's scope rules.

## 2. Verified Authorization Pipeline
 
Execution order for `POST /api/chat` is fixed and must be asserted in tests.
 
| # | Step | Owner | Failure result |
|---|---|---|---|
| 1 | `Authorization` header present and `Bearer `-prefixed | `requireAuth` | 401 `{ success:false, message:"Authentication required. Missing or malformed token." }` |
| 2 | `authService.validateSession(token, true)` | `requireAuth` | 401, body depends on `validation.code` |
| 3 | Session values copied to `res.locals` (`userId`, `email`, `role`, `permissions`, `isAdmin`) | `requireAuth` | — |
| 4 | `role === 'AUDIT_SUPERVISOR'` → unconditional deny | `requireAskVeyra` | 403 supervisor message |
| 5 | `isAdmin` OR `SITE_ADMIN` OR permissions contain `ALL` / `ASK_VEYRA` | `requireAskVeyra` | 403 privileges message |
| 6 | `if (!message)` body validation | route handler | 400 `{ error:"Message is required" }` |
| 7 | `processUserMessage(message, context)` | orchestrator | 200 / 500 |
 
### 2.1 Invariants to assert
 
1. **Authentication precedes validation.** An invalid token with a missing `message` returns **401**, not 400. This is the cheapest proof the guard runs before the handler.
2. **Supervisor denial precedes permission check.** An `AUDIT_SUPERVISOR` holding `ALL` or `ASK_VEYRA` is still 403. Confirm as intended policy and record it; do not change it.

## 3. Session Validation Codes
 
Verified in `backend/src/services/authService.ts`:
 
| Line | Condition | Code |
|---|---|---|
| 985 | token is empty string (`!token`) | `INVALID_TOKEN` |
| 1005 / 1018 | session status not ACTIVE, or inactivity timeout | `SESSION_EXPIRED` |
| 1033 | token unknown / no matching row | `SESSION_NOT_FOUND` |
| 1040 / 1054 | `expires_at` has passed | `SESSION_EXPIRED` |
 
Because the route echoes `validation.code || 'INVALID_TOKEN'`, all three codes reach the client. They are not alternatives for the same input:
 
| Request | Result |
|---|---|
| No `Authorization` header | 401, **no `code`** |
| `Authorization: Basic …` | 401, **no `code`** |
| `Authorization: Bearer ` (empty token) | 401 `INVALID_TOKEN` |
| `Authorization: Bearer invalid_token_9999` | 401 `SESSION_NOT_FOUND` |
| Expired or inactive session row | 401 `SESSION_EXPIRED` |
 
**Four distinct 401 shapes exist.** Consumers must read `code || error_code || message`; fixtures must not collapse them into one.
 
Note: the `INVALID_TOKEN` response carries the message `"Authentication required. Missing or malformed token."` taken from `authService.ts:985`, even though the header was formally well-formed. Preserve verbatim.

## 6. Evidence That Authorization Precedes Processing
 
One or both of:
 
1. Instrument `processUserMessage` with a test-only spy or counter and assert zero invocations across AV-005 … AV-009b, and exactly one for AV-010.
2. Assert no orchestrator or tool log line, and no Oracle or database access, for denied requests.
 
Preferred: both. (1) proves the code path; (2) proves no side effects.
 
AV-011 (invalid token plus empty body returns 401) is the cheapest independent corroboration that the middleware chain runs before the handler's 400 guard.
